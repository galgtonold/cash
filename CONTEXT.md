# Cash — Domain Vocabulary

Single source of truth for the terms used in this codebase. When you reach for an architectural noun, find it here first; if it's missing and load-bearing, add it.

This is **not** a tutorial. It's a glossary that disambiguates words we already use.

---

## Core concepts

**Statement** — A single top-level Python statement inside a notebook cell. Cash caches at statement granularity, not cell granularity. A cell containing three statements produces three cache entries.

**Cache key** — The deterministic identifier under which a statement's outputs are stored. Format: `stmt:{sha256(code + ':'.join(sorted(input_lineages)) + file_hash_component)}`. **All cache-key computation goes through `compute_cache_key()` in [`cache_key.py`](src/cash/notebook/cache_key.py).** See [`.github/copilot-instructions.md`](.github/copilot-instructions.md) §Critical Conventions for why.

**Lineage** — A hash chain that captures *how* a variable was produced: `hash(code + sorted(input_lineages) + file_deps)`. Two variables with the same value but different lineage are not cache-equivalent. Lineage flows through the dependency graph; cache keys are computed from it.

**LineageStore** — The single seam through which a variable's persistent lineage is read and written. Lives in [`lineage_store.py`](src/cash/notebook/lineage_store.py); held by `TrackingState.lineage`. Owns the `variable_lineage` dict and coordinates the paired `_cash_lineage_hash` attribute write so the two can never drift. Owns the priority ladder for lineage resolution (virtual → store → `_cash_lineage_hash` → compute_hash → str fallback). **Does not** own transient simulation state (`virtual_lineage` is passed in per-call) or skip-check state (`executed_input_lineages` etc. — different invariants).

**Upstream simulation** — Before running a cell, cash simulates all upstream cells to detect stale variables. The two-phase orchestrator lives in [`upstream.py`](src/cash/notebook/upstream.py) (`UpstreamChecker`); the actual simulation work lives in the **NotebookSimulator** seam.

**NotebookSimulator** — The pure-AST + cache-probing replay of upstream cells. Lives in [`notebook_simulator.py`](src/cash/notebook/notebook_simulator.py). Owned by `UpstreamChecker` (composition, not inheritance). Takes a notebook + tracking state + cache backend; produces a plan of statements to re-execute and a list of restored statements. **Never executes user code via the IPython kernel** — that's the orchestrator's job. The split exists so simulator behavior can be tested with a fake namespace, without standing up a full `Cash` instance.

**CellExecutor** — The cell-level orchestrator that runs a single notebook cell through the cache pipeline. Lives in [`cell_executor.py`](src/cash/notebook/cell_executor.py). Single entry point: `execute_cell(raw_cell, args=(), kwargs=None, original_run_cell=None) -> _PipelineCompleted | _PipelineSyntaxError | _EarlyReturn`. Both `%cash_on` (via the `pre_run_cell` hook) and `%%cash` (as the cell-magic body) delegate to it — there is **no separate code path**. Owns the phase sequence: cell-ID + notebook path → badge + timing init → module-change detection → upstream resolution → AST parse → pre-execution notifications → statement-by-statement execution. The `original_run_cell` parameter differentiates the two callers' error semantics: the hook passes its captured runner so mid-pipeline failures surface through IPython; the magic passes None so exceptions propagate to IPython's magic-error path. **Does not** own display side effects — `display()` / `publish_display_data()` calls live in the IPython adapter (`CashMagics`), invoked via a back-reference today (scaffold for a future typed `ProgressEvent` callback). **Does not** own variable restoration — that is the [[Restorer]]'s job.

**Restorer** — Owns the operation "restore one variable from cache and reconstitute its lineage in `tracking_state`." Lives in [`restore.py`](src/cash/notebook/restore.py). Single public method: `restore_variable(var_name) -> list[ProcessResult]`. Fetches the cached payload from the backend, validates file deps, reconstitutes the variable's lineage via [[LineageStore]], and recurses on missing inputs. Called by [[CellExecutor]] during upstream resolution (and, planned, by `%cash_status` for dry-run previews). **Variable-granular** (one variable + its inputs), distinct from `StatementProcessor` which is **statement-granular** (one statement + its outputs). The two operate on the same cache backend but at different units of work.

**StatementRestorer** — Restores a statement's outputs from a cached payload as one atomic unit (multiple vars + replayed stdout/stderr/rich-outputs + RNG state). Lives in [`statement_restore.py`](src/cash/notebook/statement_restore.py); owned by `StatementProcessor` as `self._stmt_restorer`. Single public entry: `restore_from_cache(cached_data, metadata, silent, process_start, render_badge)`. Plus the static `persist_metadata_only(backend, cache_key, metadata)` for the metadata-only-on-skip path. **Distinct from [[Restorer]]**: this one restores a *statement's outputs* (multiple vars at once, with display replay); Restorer restores *one variable* (no display). Different unit of work; the docstring in `statement_restore.py` spells out the boundary.

**CacheFreshnessChecker** — Decides whether a cache entry is still fresh. Lives in [`cache_freshness.py`](src/cash/notebook/cache_freshness.py); owned by `StatementProcessor` as `self._freshness`. Single public method: `check_cache(cache_key, ttl, inputs) -> (metadata, cached_data, check_time)`. Runs TTL expiry, direct file-dependency change detection, and input-file change propagation. Sets `last_miss_reason` as a side-effect so the badge can surface "why did this cell re-run?". **Distinct from [[Cacheability decision]]** (which is the *pre-execution* "should we cache this statement at all?" question); this is the *post-execution* "is the entry we already have still good?" question.

**StatementFileDeps** — Per-statement file-dependency tracker. Lives in [`statement_file_deps.py`](src/cash/notebook/statement_file_deps.py); owned by `StatementProcessor` as `self._file_deps`. Public methods: `update_for_var`, `inherit_from_inputs`, `restore_from_metadata`. Plus module-level pure helpers `compute_file_hash_component(accessed_files)` and `read_module_source_hash(mod_file, dep_files)` used by sibling sub-systems. **Distinct from [[file_tracker]]** (the import-hook layer that intercepts `pd.read_csv` / `open` at runtime): this manages *which files contributed to producing each variable* (transitively through inputs); the import hook records *which files were accessed during a single execution*.

**StatementLineageBuilder** — Computes lineage hashes for statement outputs. Lives in [`statement_lineage.py`](src/cash/notebook/statement_lineage.py); owned by `StatementProcessor` as `self._lineage`. Two public methods: `capture_and_track_variables(outputs, inputs, code, source_hash, cache_key, accessed_files, tree)` and `build_output_lineages(outputs)`. Owns input-lineage assembly, function-source hashing, module-source hashing (both `import X` and `from X import Y` cases), per-variable content hashing, and granular module-attribute dependency tracking. **Carries the heaviest state surface of the StatementProcessor siblings** — it needs many tracking-state dict refs plus three processor-owned dicts (`_granular_preserved_vars`, `module_attribute_deps`, `from_import_sources`). The cost of consolidating lineage-building into one cohesive class.

## Architectural terms

**Cacheability** — The property *"can this statement be cached?"*. Distinct from *"should the user have asked for it?"* (annotations) and *"has it been cached before?"* (cache hit). Cacheability is a pure-AST decision: given the code, are there in-place mutations, side effects, or stateful calls that would make caching unsound? Lives in [`cacheability.py`](src/cash/notebook/cacheability.py).

**StatementAnalysis** — Value object returned by `analyze_statement(code, tree, outputs)`. Carries everything the AST can tell us about a statement: `top_level_mutated_vars`, `all_mutated_vars`, `side_effects`, `called_names`. Pure data + a `skip_reasons(outputs)` helper that turns findings into human-readable strings for `metrics['uncacheable_reasons']`. **Does not** know about user_ns, decorators, or annotations — those are caller concerns.

**Annotation** — A `@cash:` comment directive (`no_cache`, `ttl`, `persist`, `allow-random`) that the user writes in the source. Parsed in [`annotations.py`](src/cash/notebook/annotations.py) into a `CacheAnnotation`. Distinct from cacheability: annotations are *user input*, cacheability is *code analysis*. The **cacheability decision** merges them.

**Cacheability decision** — The runtime merge that combines `StatementAnalysis` (pure AST) with the `CacheAnnotation`, the `@stateful` registry, the forbidden-function scan, and the lineage state into one verdict: `(cacheable, reasons)`. Lives in [`cacheability_decision.py`](src/cash/notebook/cacheability_decision.py) as the module-level function `decide_cacheability`. **Five reason-sources, first wins, deterministic order**: `@cash:no-cache` → forbidden functions → `@stateful` calls → mutations/side effects → missing input lineage. The function takes runtime hooks (purity lookup, forbidden scan, skip-variable predicate) as callables so this module does not import `purity` or `analysis` — every input the decision reads is in the signature. Distinct from `cacheability.py`, which is *pure-AST only* by design.

**Purity / Stateful** — A function-level marker. `@pure` declares "calling me produces no observable state change"; `@stateful` declares the opposite. Lives in [`purity.py`](src/cash/notebook/purity.py) and is part of the **public API** (re-exported from `cash`). Cacheability *consumes* the purity registry via name-resolution against `user_ns`; it does not own it.

**Control-structure handler** — Strategy object that owns the per-iteration / per-statement decomposition of one control-flow shape. `ForLoopHandler`, `IfHandler`, and `TryHandler` live in sibling modules (`control_for_handler.py`, `control_if_handler.py`, `control_try_handler.py`); the orchestrator in [`control_structures.py`](src/cash/notebook/control_structures.py) (`ControlStructureProcessor`) dispatches to them and keeps only the single-unit fallback for `while` / `with` / break-continue loops. Shared lineage / mutation / badge / error helpers live in [`control_structure_helpers.py`](src/cash/notebook/control_structure_helpers.py) and are imported by all handlers — handlers never call back into each other.

**BadgeView** — Component-tree IR for badge rendering. A semantic description of *what to show* in a badge, independent of output format. Nodes are React-component-shaped (`InteractiveBadge`, `StatusBadge`, `Section`, `StatementRow`, `ForLoopGroup`, `LoopStatement`, `IterationRow`, `ControlGroup`, `ControlGroupSingle`, `ControlBody`, `SkippedBucket`, `DecoratorCallGroup`, `DecoratorCall`, `OverheadBreakdown`, `BugReportLink`) with semantic props (`status='restored'`, not `color='#006644'`). Built from `ProcessResult` metrics by the view-builder in [`badge_renderer/view_builder.py`](src/cash/notebook/badge_renderer/view_builder.py); node types live in [`badge_renderer/view.py`](src/cash/notebook/badge_renderer/view.py). Consumed by renderers under [`badge_renderer/renderers/`](src/cash/notebook/badge_renderer/renderers/): `HtmlRenderer` (the v3 "code-first" design — see below), `TextRenderer`, and a future `ReactRenderer` that mounts components from the same tree. Renderers own all styling decisions (colors, fonts, layout) via [`badge_renderer/theme.py`](src/cash/notebook/badge_renderer/theme.py); the IR carries no presentation values. **Every new badge variant adds a node and a renderer method, never a new dispatch ladder.**

**v3 design** — Current visual language for the HTML badge, ported from `design/notebook-badges/Badge.v3.jsx` (the Cash Design System handoff). Code-first layout: each row is a 5-column CSS grid of *[state rail · syntax-highlighted code · RAM/DISK tier dots · per-row timing bar · state-tinted time chip]*. Loops collapse via nested `<details>` with an inline iteration mini-histogram and a per-iteration drill-down. The summary chip carries a sparkline (one bar per top-level current row) and static state-count chips. Styling is hoisted into a single `<style>` block per badge; all class names are prefixed `c3-` (a stable test contract). **Notebook constraint**: every expansion uses `<details>`/`<summary>` and every state cue is pure CSS (`:hover`, `[open]`, `[data-kind]`). No inline `onclick`, no script tags — VS Code's notebook renderer sanitises those, and the design must look identical in classic Jupyter, JupyterLab, and VS Code. Python keyword/string/comment highlighting is done at render time by [`renderers/_pytoken.py`](src/cash/notebook/badge_renderer/renderers/_pytoken.py) — a tiny regex tokenizer, not Python's `tokenize` module (badge inputs are single lines and may be syntactically incomplete).
